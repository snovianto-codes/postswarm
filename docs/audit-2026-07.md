# PostSwarm Audit — 2026-07-12

Read-only review of the repo as it actually exists, ahead of the multi-model /
governance extension. No code changed for this report.

**Headline finding, read first:** the pipeline this repo implements does not
match the pipeline described in the extension request. See [§0](#0-mismatch-between-the-request-and-the-repo)
before reading the rest — it affects how every later phase should be scoped.

---

## 0. Mismatch between the request and the repo

The request describes PostSwarm as "Scout, Filter, Drafter, Verifier, with
Telegram human approval before posting." The repo contains none of that:

| Requested | Actual repo |
|---|---|
| Agents named Scout, Filter, Drafter, Verifier | 9 agents: Feed, Editor, Research (Web + Fact Checker + Devil's Advocate), Perspective, Hook, Writer — see §1 |
| Telegram bot for approval | No Telegram code anywhere. `grep -ri telegram` across `agents/`, `hermes/`, `*.py`, `*.html` returns zero hits — the only mention in the whole repo is one line in the README's "What's next" wishlist (`README.md:210`), i.e. an unbuilt idea, not a control |
| A gate that stands between drafting and posting | There is no programmatic posting at all. LinkedIn is never called via API. The human reads the draft in the browser UI, clicks "Copy to clipboard" (`PostSwarm.html:360-361`, `navigator.clipboard.writeText`), and pastes it into LinkedIn's own compose box by hand. `/feed/mark_posted` (`agents/feed_agent.py:223-236`) just flips a `posted` flag in SQLite for dedup — it does not publish anything |

Net effect: there is no approval *gate* to preserve because there is no
auto-post path to gate in the first place — every post leaves this system
only via manual copy-paste, which is a strictly stronger guarantee than a
Telegram approve/reject button would be (nothing in the code can ever publish
on your behalf, full stop).

This matters for scoping the later phases:

- **Phase 1's config template** names roles `scout / filter / drafter /
  verifier`. The actual roles are `feed / editor / web / fact / devil /
  perspective / hook / writer` — 8 roles, not 4, and no single one of them is
  a "verifier" that gates output (Fact Checker labels claims but doesn't
  block the pipeline — see §3). The closest match to "Drafter" is `writer`.
- **Phase 3's audit log spec** asks for "approval outcome: approved /
  rejected / edited, approver, and timestamp from the Telegram interaction."
  Today there is no event to capture here — approval happens outside the
  app's observability, on linkedin.com, in the user's head. Logging it would
  require either (a) documenting the manual-copy flow as the control instead
  of a Telegram event, or (b) building new Telegram delivery as net-new
  scope — which is a bigger addition than "preserve the existing gate."

**I'd like your call before Phase 1** on how to treat this — see the
question at the end of this report. Everything below describes the repo as
it is.

## 1. Actual architecture

Nine independent Flask processes, started by `start.sh`, each on its own
port, talking to each other over `localhost` HTTP (`requests`), coordinated
by the Orchestrator which also serves the single-file React frontend. No
message queue, no shared client, no SDK abstraction — every agent that calls
an LLM constructs its own `google-genai` client inline.

```
Orchestrator (agents/orchestrator.py, :8080)
  serves PostSwarm.html, coordinates SSE pipeline, proxies feed/digest endpoints
  │
  ├─ Feed Agent      agents/feed_agent.py       :5008   RSS crawl (19 sources), SQLite dedup — no LLM call
  ├─ Editor Agent     agents/editor_agent.py     :5009   ranks feed items → top-N picks           — Gemini
  ├─ Research Agent   agents/research_agent.py   :5001   fans out to Web/Fact/Devil, no LLM itself — HTTP only
  │    ├─ Web Agent           agents/web_agent.py           :5002   fetch URL or generate research pts — Gemini
  │    ├─ Fact Checker        agents/factchecker_agent.py   :5003   labels claims VERIFIED/etc          — Gemini
  │    └─ Devil's Advocate    agents/devils_advocate_agent.py :5004 counter-arguments                   — Gemini
  ├─ Perspective Agent agents/perspective_agent.py :5005   SEA/role-specific insights                — Gemini
  ├─ Hook Agent        agents/hook_agent.py       :5006   5 opening-line variants                    — Gemini
  └─ Writer Agent      agents/writer_agent.py     :5007   assembles final post from VOICE.md + above — Gemini
```

`hermes/prefetch.py` is a tenth, standalone entry point (run via cron/Hermes,
not part of `start.sh`) that re-implements the Feed→Editor flow directly in
one script — it imports `feed_agent.fetch_all()` and duplicates
`editor_agent.py`'s ranking prompt verbatim (see §6).

**Wiring**: every LLM call goes through the official `google-genai` Python
SDK (`from google import genai`), never raw HTTP. Every agent that calls
Gemini builds its own client via a local `_get_client()` function that reads
`GEMINI_API_KEY` from `.env` on every call (so key rotation doesn't need a
restart — see commit `1b607b3`). There is no shared client module; the same
~4-line client constructor is copy-pasted into 6 files (`web_agent.py`,
`factchecker_agent.py`, `devils_advocate_agent.py`, `perspective_agent.py`,
`hook_agent.py`, `writer_agent.py`, `editor_agent.py`, plus `orchestrator.py`
and `hermes/prefetch.py` each have their own variant).

Two agents never call an LLM: **Feed** (pure RSS/SQLite) and **Research**
(pure HTTP fan-out/aggregation — it calls Web, Fact, and Devil over HTTP and
returns their combined JSON).

## 2. Where model names/providers are hardcoded

Only one provider exists in this repo: Google Gemini, via `google-genai`.
There is no OpenRouter, Anthropic, or Ollama code, dependency, or env var
anywhere (`requirements.txt` lists only `google-genai==1.2.0`).

Model identity is hardcoded — as a string literal — in every one of these
locations:

| File | Line(s) | What's hardcoded |
|---|---|---|
| `agents/orchestrator.py` | 52-53 | `ALLOWED_MODELS = {'gemini-3.1-pro-preview', 'gemini-2.5-pro', 'gemini-2.5-flash'}` |
| `agents/orchestrator.py` | 145 | `'model': 'gemini-2.5-flash'` (digest ranking call, not user-selectable) |
| `agents/orchestrator.py` | 269 | default for `/run?model=` query param |
| `agents/orchestrator.py` | 541 | startup key-validation ping, `model='gemini-2.5-flash'` |
| `agents/writer_agent.py` | 22, 46 | `FALLBACK_MODEL = 'gemini-2.5-flash'`, `ALLOWED_MODELS = {...}` (same 3-model set) |
| `agents/editor_agent.py` | 26-27 | `DEFAULT_MODEL`, `ALLOWED_MODELS` (same set) |
| `agents/research_agent.py` | 48-49 | `ALLOWED_MODELS`, `DEFAULT_MODEL` (same set, though only used to pass through to sub-agents) |
| `agents/web_agent.py` | 24 | `DEFAULT_MODEL = 'gemini-2.5-flash'` — model is **not** user-selectable here; line 132 ignores any incoming `model` field and always uses the default |
| `agents/factchecker_agent.py` | 20, 32 | same pattern; model also fixed regardless of caller input (line 33 comment: "fixed: structured labeling task") |
| `agents/devils_advocate_agent.py` | 20, 32 | same pattern, also fixed |
| `agents/perspective_agent.py` | 20, 33 | same pattern, also fixed |
| `agents/hook_agent.py` | 20, 33 | same pattern, also fixed |
| `hermes/prefetch.py` | 26-27 | `DEFAULT_MODEL`, `FALLBACK_MODELS = [DEFAULT_MODEL, 'gemini-2.5-pro']` |

The `{'gemini-3.1-pro-preview', 'gemini-2.5-pro', 'gemini-2.5-flash'}`
allowlist literal is duplicated **eight times** across the codebase (every
agent file plus the orchestrator). It is not imported from a shared
constant. Five of those eight agents (Web, Fact Checker, Devil's Advocate,
Perspective, Hook) declare the allowlist but then never consult it —
they silently ignore the caller-supplied `model` and always run
`gemini-2.5-flash`, by design ("fixed" comments), which means today only
**Writer, Editor, and the Orchestrator's digest/health-check paths** are
actually multi-model-selectable at the API level, and only between three
Gemini variants.

**Current default model** (the one to use for the Phase 1 `config/models.yaml`
"identical to today" baseline): **`gemini-2.5-flash`**, with `gemini-2.5-pro`
as the user-selectable upgrade and `gemini-3.1-pro-preview` also allowed.
Writer and Editor both fall back to `gemini-2.5-flash` on failure
(`writer_agent.py:162-176`, `editor_agent.py:101-135`); that fallback logic
is hand-rolled per-file, not shared.

## 3. Logging today

All logging is `print()` to stdout, redirected by `start.sh` to
`logs/<agent>.log` (one file per process, gitignored, no rotation, no
structure — plain text with `[Agent Name]` prefixes and timestamps only on
the Orchestrator's own lines via `ts()`). There is no structured/JSON log,
no log aggregation, and no persistence beyond the current run of the
process (logs overwrite/append across restarts with no rotation).

The only persistent store is `data/seen.db` (SQLite), which records per-item:
`hash, title, url, source, summary, ts, tier, dismissed, posted`. It has no
concept of a "run," no model name, no draft content, no timestamps for when
a post was actually copied out, and no user identity (there's only one
user).

Daily digest JSON (`data/digest_YYYY-MM-DD.json`) caches the picks for the
day but is overwritten by `/digest/refresh` and contains no model/cost/run
metadata — just the picks and scan stats.

**Directly answering your question — "which model drafted the post that
went out last Tuesday, what sources did Scout pull, what did the Verifier
flag, and when did I approve it?"** — no, none of this is answerable today:

- *Which model drafted it*: not persisted. `writer_agent.py` returns
  `model_used` in its HTTP response and the Orchestrator SSEs it to the
  browser (`agent_detail` event, `orchestrator.py:517-520`) and prints it to
  stdout/`logs/orchestrator.log` (line 521) — but nothing writes it to a
  file keyed by post or date. It's gone once the SSE connection closes,
  unless you happen to still have that day's terminal scrollback.
- *What sources Scout (Feed Agent) pulled*: partially — `seen.db` has every
  RSS item ever seen with its URL and timestamp, but nothing links a
  specific fetch batch to a specific drafted post.
- *What the Verifier (Fact Checker) flagged*: not persisted at all. Fact
  Checker's VERIFIED/NEEDS_CAVEAT/UNVERIFIED labels
  (`factchecker_agent.py:44-49`) exist only inside the HTTP response for that
  one request; the Research Agent discards the labels and forwards just the
  cleaned text (`research_agent.py:83-85`) — the label itself never reaches
  the Writer, the frontend, or any log.
- *When you approved it*: there is no approval event to timestamp — see §0.
  The closest analog, `/feed/mark_posted`, records only a boolean flip in
  `seen.db`, no timestamp column is even read back for it (there is a `ts`
  column but it's the original article's publish time, not the mark-posted
  time).

So: correct, this is exactly the gap Phase 3 is meant to close, and it's a
real gap, not just an inconvenience — today none of those four questions are
answerable even in principle from stored data.

## 4. Human approval gate

There is no dedicated "gate" component — the architecture doesn't build a
posting action for the human to approve or reject in the first place.
Concretely:

- The Orchestrator's pipeline (`make_pipeline`, `orchestrator.py:335-530`)
  ends at `yield sse({'type': 'done', 'post': final_post, ...})` — it hands
  the draft back to the browser over SSE and stops. Nothing downstream of
  that ever touches an external posting API.
- `PostSwarm.html` renders the draft with a **Copy to clipboard** button
  (`navigator.clipboard.writeText`, line 361) as the only exit path for the
  text. The human pastes it into LinkedIn's own web UI outside this app.
- `POST /feed/mark_posted` (`orchestrator.py:220-227` → `feed_agent.py:223-236`)
  is a manual bookkeeping action the user clicks in the UI *after* they've
  posted by hand, purely to keep the Editor's "recent posted" dedup list
  accurate. It has no causal effect on anything being published, and
  nothing else calls it — it can't be reached from any automated code path.
- No code path bypasses "approval" because there is no code path that
  posts. Grepping the whole repo for LinkedIn API clients, OAuth tokens, or
  any outbound call to a social platform's write endpoint returns nothing —
  `PostSwarm.html` and `bookmarklet.js` only ever *read* from
  linkedin.com (the bookmarklet scrapes a post you're viewing, for
  inspiration capture; it also never posts).

Bottom line: the "gate" today is 100% the fact that publishing requires a
human's hands on LinkedIn's own website. It's implicit and un-auditable
(§3), but it is also un-bypassable by construction, since there's nothing to
bypass into.

## 5. Aggregator-source detection badge

Entirely client-side, entirely in `PostSwarm.html`:

- `AGGREGATOR_DOMAINS` (`PostSwarm.html:535-541`) is a hardcoded `Set` of
  known newsletter/aggregator hostnames.
- `isAggregator(url)` (line 542-545+) parses the URL's hostname and checks
  set membership.
- Called at render time in two places: the daily-brief pick cards (line
  587, shows a warning tooltip icon) and the "all stories" browse list
  (line 731, shows a `∑` marker).

The result is **never computed server-side and never stored** — no field
in `seen.db`, no field in the digest JSON, nothing sent to any agent. It's
recomputed from the domain set on every render, purely a UI hint to the
human before they draft/post. This matters for Phase 3.2 (data-flow map):
there's no "aggregator-badge result per source" to log from the backend
today; it would need to be either (a) moved server-side, or (b) sent up
from the frontend at draft time if you want it in the audit trail.

## 6. Fragile, duplicated, or surprising

- **Model allowlist/fallback logic duplicated 8×, not centralized.** Any
  future model addition today means editing the same set literal in 8
  files and hoping you don't miss one (`gemini-3.1-pro-preview` was added
  in commit `cbfc126` — worth checking that commit touched all 8 if you
  want a sense of how error-prone this already is).
- **Five of eight LLM-calling agents ignore the model the caller passes.**
  Web, Fact Checker, Devil's Advocate, Perspective, and Hook all declare
  `ALLOWED_MODELS` but then hardcode `model = DEFAULT_MODEL` regardless of
  input (each has a "fixed: ... no need for smarter model" comment). Only
  Writer and Editor actually honor the caller's model choice today. Phase 1
  should treat this as intentional-but-worth-confirming, not a bug to
  silently "fix" by making them user-selectable — that's a behavior change
  outside a pure abstraction refactor.
- **`hermes/prefetch.py` duplicates `editor_agent.py`'s ranking prompt
  verbatim** (compare `editor_agent.py:66-99` and `prefetch.py:79-112` —
  identical text, hand-copied). A prompt change in one will silently drift
  from the other unless someone remembers both. Same for the
  `ALLOWED_AI_FIELDS` allowlist pattern. Worth pointing your model-client
  refactor at unifying this rather than adding a third copy.
- **Stray `.claude/worktrees/` directories** (`modest-payne-671d34`,
  `pedantic-spence-c41a74`, `relaxed-lalande-2e134f`, `reverent-lewin-0e45ac`,
  `youthful-yonath-482182`) contain leftover copies from past Claude Code
  sessions — and some of them (`modest-payne`, `relaxed-lalande`) contain
  files from a **completely different project**
  (`Documents/Python/OpenClaw/Daily-OC/*.py` — crypto/gold price alerts,
  Gmail summaries) that have nothing to do with PostSwarm. These are
  gitignored (`.claude/` is in `.gitignore`) so they won't land in commits,
  but they'll pollute any repo-wide grep/search you or I run later
  (they already showed up in my first `find` pass on this audit). Worth a
  `rm -rf .claude/worktrees/*` cleanup before Phase 1, at your discretion —
  read-only audit, so I didn't touch it.
- **No automated tests exist anywhere** in the repo (no `test_*.py`,
  no `pytest` in `requirements.txt`). Phase 1's request to "run whatever
  tests or a dry-run exist after each [agent refactor]" will mean dry-run
  only — there's no test suite to fall back on.
- **No `--dry-run` flag exists yet** on the Orchestrator or anywhere else —
  confirmed by reading `orchestrator.py` end to end; the only way to see a
  pipeline run today is the live SSE stream to the browser (or the
  `logs/*.log` output). Phase 1.4 will need to build this from scratch, not
  extend an existing flag.
- **Client re-created per-LLM-call, by design** (`_get_client()` reads
  `.env` fresh every time), so `GEMINI_API_KEY` rotation doesn't need a
  restart — this is deliberate (commit `1b607b3`) and should be preserved
  by any model-client abstraction, not "optimized away" into a
  cached/singleton client.
- **`agents/research_agent.py` is a pure HTTP fan-out node with no LLM
  call of its own** — worth remembering in Phase 1 so it isn't
  accidentally given a `config/models.yaml` entry that does nothing (there's
  no model to swap for it; whatever role key you invent for it should map
  to "no-op" or simply not exist in the config schema).
- **SSRF/URL-fetch hardening lives only in `web_agent.py`**
  (`_validate_url`, `_NoRedirect`, DNS-resolution IP-range checks,
  `web_agent.py:69-102`) — if Phase 2's MoA references ever fetch external
  content themselves (they shouldn't; they only see the brief +
  `VOICE.md` + role_hint per the spec), this is the pattern to reuse rather
  than reinvent.
- **Orchestrator's `ALLOWED_HOSTS`/`Sec-Fetch-Site` guard**
  (`orchestrator.py:25-39`) is specific to this being a localhost-only
  prototype; nothing to change here for Phase 1-3, just noting it's the
  one real "security boundary" in the app and it has nothing to do with
  model calls.

## Summary for you

1. **The repo is real and coherent, just not the repo the request describes.**
   It's a "Today's Brief + Write Post" LinkedIn co-pilot with 9 Gemini-only
   agents, zero auto-posting, zero Telegram. Every post leaves the system
   via manual copy-paste onto linkedin.com.
2. **Current default model**: `gemini-2.5-flash` (fallback for Writer/Editor
   too), with `gemini-2.5-pro` and `gemini-3.1-pro-preview` also allowed.
   Use `gemini-2.5-flash` as the "identical to today" baseline for Phase 1's
   `config/models.yaml`.
3. **Model config is scattered 8 ways**, and 5 of 8 LLM agents currently
   ignore the caller's model choice by design — Phase 1 needs to decide
   whether to preserve that "fixed model" behavior per-agent or make
   everything configurable (I'd default to preserving it unless you say
   otherwise, since making previously-fixed agents configurable is a
   behavior change beyond "abstract the plumbing").
4. **Zero audit trail exists today** — your four example questions (model
   used, sources pulled, verifier flags, approval time) are all
   unanswerable from stored data right now. This is a real, confirmed gap.
5. **No bypassable gate exists because no auto-post path exists.** The
   human's hands-on-keyboard copy-paste onto linkedin.com *is* the gate.
6. **Aggregator badge is frontend-only**, recomputed per render, never
   persisted — Phase 3's data-flow/audit-log will need a decision on
   whether to move it server-side or capture it from the frontend at
   draft-time.
